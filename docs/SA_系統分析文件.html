系統定位

不追求通用 HR SaaS 的完整度，而是精準對齊 Think4U 的實際規則（彈性工時 09:30–10:00、計薪 30 天制、特休週年制+曆年使用）。因此大量邏輯是「寫死的公司規則」——這是有意的設計決策。

原本的問題系統解法
員工出勤靠 Excel 人工彙整、易錯GPS 手機打卡 + 自動出勤判定 + 月度矩陣統計
薪資試算靠人工查勞健保級距表內建 2025 台灣級距表 + 自動計薪（含請假扣薪、到職比例）
請假／加班簽核走紙本或口頭多角色線上簽核流程 + 稽核軌跡

使用者角色與權限模型

接手時最容易搞混的地方系統有兩套疊加的權限機制：Django Group（角色）與 AdminAccessGroup（前後台分離）。判斷「這個人能看什麼」時必須同時看兩者。

① Django Group（角色）

角色典型使用者主要能力
系統管理員Steven、Tiffany全系統（acts_as_superuser）
人資 HRHR 人員全公司員工資料、薪資、二層簽核
部門主管各部門主管自部門（含子部門）、一層簽核、指派加班
一般員工全體僅自己的資料

② AdminAccessGroup（Think4U 自製，4 個旗標）

旗標意義
can_access_admin能否進後台（否則一律導向 /portal/）
force_admin_only強制只能用後台（高管不需打卡前台）
show_in_personal_reports是否出現在個人出勤／請假報表（高管隱藏）
acts_as_superuser該角色成員視為 superuser

③ 主管判定的特殊設計

「主管」= Horilla 原生直屬主管（reporting_manager_id） ∪ Think4U 部門主管（Department.manager，含子部門遞迴）。兩者聯集是因為公司實際上兩種關係都在用。

務必遵守新增任何「主管才能看」的頁面，一律用 manager_utils.is_manager() 與 managed_employees()，不要用 Horilla 的 is_reportingmanager——曾因此造成部門主管看不到簽核頁的 bug。

分層結構、技術選型理由、請求生命週期、效能設計、部署拓撲，以及架構弱點與改善建議。

分層結構

為什麼「規則層」要獨立成 pure functions

attendance_rules.py 和 payroll_rules.py 完全不碰 DB、不 import Django model，輸入輸出都是原生型別。這是本系統最重要的架構決策：

好處實際效益
可單獨測試不用建資料就能驗算（特休 15 案例測試靠這個）
可重複使用同一份計薪邏輯被「月度頁／即時 AJAX 儲存／Excel 匯出」三處共用，保證三處數字一致
規則變更好定位勞健保級距調整只改常數，不動 view
接手守則任何「算錢、算時數、算天數」的邏輯都寫進規則層，view 只負責取資料和呈現。若在 view 裡寫計算，就會出現「頁面顯示與匯出 Excel 不一致」的經典 bug。

技術選型與理由

決策選擇理由代價
基底fork Horilla員工／部門／請假基礎 model 現成，省數月開發綁死其架構、升級困難
前端HTMX + Template1 人開發無需前後端分離；SSR 首屏快複雜互動難做
部署Docker Compose環境一致、DB 版本可控正式機需 rebuild 才生效
客製隔離獨立 think4u/ app與上游程式分離，易識別少數原生檔仍需修改
計薪自製而非 Horilla payroll台灣勞健保規則差異太大自行維護級距表
認證Django session + 自寫 OAuth不引入 allauth，減少依賴自行維護 OAuth 流程
為什麼不用 Horilla 原生的 Attendance

Horilla 的 Attendance / AttendanceLateComeEarlyOut 設計與台灣彈性工時規則不符，且需搭配其 shift/work_type 體系。決策：只寫 AttendanceActivity（打卡明細），出勤狀態一律即時計算，不落地儲存判定結果。

優點規則調整後，歷史資料的判定自動跟著更新（不需回溯批次）
缺點每次看報表都要重算 → 月度頁需一次撈全月資料在記憶體算

請求生命週期

Request │ ├─ ServerTimingMiddleware（自製） → 量測並回寫 X-Server-Time ├─ SecurityMiddleware / WhiteNoise → 安全標頭、靜態檔 ├─ SessionMiddleware / CommonMiddleware ├─ LocaleMiddleware → zh-Hant ├─ CsrfViewMiddleware ├─ AuthenticationMiddleware → request.user ├─ MessageMiddleware / XFrameOptions └─ AdminAccessGateMiddleware（自製） → ★前後台守門 ├─ force_admin_only 角色 + 訪問前台 → redirect / └─ 無後台權限 + 訪問後台 → redirect /portal/ ▼ View（權限二次判定）→ 規則層計算 → Template / JsonResponse ▼ Signals：audit_log post_save/post_delete → 寫 AuditLog
新增公開頁面（登入前可見）必須加進 ALLOWED_PREFIXES，且前綴不要帶結尾斜線（/logout 不是 /logout/），否則會被守門 middleware 導走。

效能設計（已完成三輪優化）

現況：一般頁面 warm < 100ms、47–72 queries。

問題根因解法效果
每頁 60+ 多餘 SQLHorillaCompanyManager 每次跑兩條 COUNT 偵測重複結果 cache 在 process-wide dictquery 降 40–65%
部門／職位頁 N+1逐筆再查員工數annotate(Count(distinct=True))124→50 queries
換頁載入慢每頁載 ~29 個外部 JS，含 4.9MB 未使用的 pivottable刪除無用 JS每頁少 4.9MB
「第一下卡、第二下秒回」gunicorn 預設 1 個 sync worker改 gthread，2×4（正式 3×4）併發不再序列化
新增員工頁 cold 9.6sview 內建未使用的 form/filter移除無用物件0.79s
月度統計頁的效能策略（最重的一頁）

需算「N 員工 × 31 天」的矩陣，策略：

  1. 一次撈完該月所有 AttendanceActivity、LeaveRequest、Holidays（3 次 query，非 N×31 次）
  2. 在記憶體整理成 by_emp_date / leave_minutes_by_emp_date 字典
  3. 迴圈內只做純計算（呼叫 evaluate()），不再碰 DB
維護注意改這頁時務必維持此模式。曾因在迴圈內計算請假分鐘導致 AttributeError 與效能退化。

其餘 12 張表的 Schema

MonthlyPayExtra — unique(employee, year, month)

8 個變動加項：overtime_pay（加班費）、unused_annual_leave（特休未休）、birthday_gift／dragonboat_gift／midautumn_gift（三節禮金）、expense_reimbursement（代墊費用）、perfect_attendance_bonus（全勤獎）、admin_assistant_fee（行政助理費）。property total = 8 項加總；常數 EXTRA_PAY_FIELDS。

注意這些不計入勞健保投保薪資，只在最後加回實領。

HealthInsuranceDependent

name / relationship / national_id / birth_date / enroll_date / is_enrolled。helper sync_dependent_count(employee) 重算並寫回 EmployeeSalary.dependents。健保計費眷屬上限 3 人（在 payroll_rules 限制）。

LeaveAllocation（特休配額，Model B 核心）

每個週年日產生兩筆：當年剩餘段 + 隔年完整段。欄位：service_years（年資）、anniversary_date（獲假日）、tier_days（級距天數）、grant_type（anniversary／carryforward）、days_granted、days_used、start_date～end_date（可請休區間）。

AnnualLeaveRecord（舊制）

year / allocated_days / used_days / carried_over / carry_over_expire / source。新功能不要用這張表（已被 LeaveAllocation 取代）。

LeaveGrantRequest（給假申請）

leave_type / requested_days / reason / proof_document（FileField）/ status（pending·approved·rejected）/ granted_days（HR 實際核發，可與申請不同）/ hr_note / decided_by / decided_at。核准時自動建立或加值 AvailableLeave。

OvertimeAssignment（主管指派，7 狀態機）

狀態：pending_employee（初始）→ employee_confirmed / employee_rejected → pending_hr → hr_approved（終）/ hr_rejected（終）；cancelled（僅初始狀態可取消）。另有 employee_note / hr_note / employee_confirmed_at / hr_approved_at。

OvertimeApplication（員工申請）

與上表並存但走 ApprovalWorkflow 多關卡：workflow / current_step_order / decisions(JSON)。

PunchCorrectionRequest（補打卡）★多關卡範本

target_date / requested_check_in / requested_check_out / reason / status / workflow / current_step_order / decisions(JSON)。

唯一真正在跑 ApprovalWorkflow 的模組可作為 Phase 4 的實作範本。decisions JSON 結構：每關的 {order, approver_id, decision, note, at}。最後一關核准 → 自動寫入 AttendanceActivity，status 轉 applied。

ApprovalWorkflow / ApprovalStep

Workflow：job_position（每職位一組）+ request_type（leave／overtime／punch_correction）+ is_active。
Step：order（關卡順序）+ approver_type（direct_manager／department_head／role／employee／hr）+ approver_role（FK Group）／approver_employee（FK Employee）。

AdminAccessGroup（1:1 Group）

判定順序

計薪演算法 ★核心

全域規則值
計薪基準30 天（PAYROLL_BASE_DAYS），日薪 = 全薪 ÷ 30
金額取整一律無條件進位到元（math.ceil），且「先進位再做後續計算」
全薪（gross）本薪 + 伙食 + 交通 + 管理加給 + 技術管理加給 + 薪資加給

勞保／健保自付額

投保級距 = 第一個 >= 投保薪資的級距值 勞保自付 = ⌈級距 × 12.5% × 20%⌉ （12.5% = 普通事故 11.5% + 就保 1%） （上限級距 45,800） 健保自付 = ⌈級距 × 5.17% × 30% × (1 + min(眷屬,3))⌉
投保薪資的來源（優先序）labor_insured_salary > 0 → 用它；= 0 → fallback 用全薪。
設計理由：實務上投保薪資由 HR 依級距表指定，不應與薪資欄位連動（可能刻意低報或有上限）。

請假扣薪

日薪 = ⌈全薪 ÷ 30⌉ ← 先進位 各假別扣薪 = ⌈(1 − 給薪比例) × 日薪 × (該假別時數 ÷ 8)⌉ ← 各自進位 總扣薪 = Σ 各假別扣薪 ← 進位後才加總 （保證明細 = 總額）
假別比例扣薪法源
事假0.0全扣勞工請假規則 §7
病假（普通傷病）0.5半扣勞工請假規則 §4
生理假0.5半扣性平法 §14
特休／公假／婚假／喪假／產假／產檢假／陪產假／公傷病假／補休1.0不扣—
未列出的假別1.0不扣（安全預設）—
薪資試算器 實作 payroll_rules.compute_salary()／2025 級距

到職當月比例計薪

到職日 <= 當月 1 日 → 比例 1.0（整月） 到職日 > 當月最後一日 → 比例 0.0（尚未到職，完全不計薪、不計勞健保） 到職當月 → 比例 = (當月最後一日 − 到職日 + 1) ÷ 當月天數 ↑ 在職日曆天數（非工作日數） 應發全薪 = ⌈全薪 × 比例⌉

同時影響出勤：到職前的日子標記 pre-hire，不算應出勤、不算缺勤；月度摘要的「應出勤天數」改為該員工當月實際在職的工作日數。

Google SSO 整合

OAuth 2.0 Authorization Code Flow（google_auth.py，自寫不用 allauth）

[1] GET /think4u/google/login/?dest=portal|admin → 產生隨機 state 存 session（防 CSRF）；dest 存 session → 302 到 accounts.google.com/o/oauth2/v2/auth scope="openid email profile", prompt=select_account, hd=think4u-tech.com（提示預選公司網域） [2] 使用者選帳號 → Google 302 回 /google/callback?code=&state= [3] 後端驗證： state 相符？（pop session，防重放） → POST oauth2.googleapis.com/token 換 id_token → 解 JWT payload，驗 iss / aud == CLIENT_ID / email_verified → 驗 email 網域 ∈ GOOGLE_OAUTH_ALLOWED_DOMAINS → 以 email 找既有 User（★找不到則拒絕，不自動開帳號） → 檢查 user.is_active、employee 存在且 active → login() → 依 dest + 角色導向
redirect_uri 必須完全一致Google Console 登記值為 https://hrms.think4u-tech.com/google/callback（根路徑、無結尾斜線）。_redirect_uri() 對非 localhost 主機強制改寫為 https（DEBUG 下 Django 看不到 X-Forwarded-Proto 會誤判 http，造成 redirect_uri_mismatch）。

範例 A：新增「簽核類型」（如加薪申請）

最推薦作法：照抄 PunchCorrectionRequest（唯一完整走 ApprovalWorkflow 的模組）。

# 1) think4u/models.py
class SalaryRaiseRequest(models.Model):
    STATUS_CHOICES = [("pending", _("待審核")), ("approved", _("已核准")),
                      ("rejected", _("已駁回"))]
    employee = models.ForeignKey(Employee, on_delete=models.CASCADE,
                                 related_name="salary_raise_requests")
    current_salary = models.PositiveIntegerField(verbose_name=_("現行薪資"))
    requested_salary = models.PositiveIntegerField(verbose_name=_("建議薪資"))
    reason = models.TextField(verbose_name=_("理由"))
    status = models.CharField(max_length=20, choices=STATUS_CHOICES, default="pending")
    # ★ 多關卡三本柱
    workflow = models.ForeignKey("think4u.ApprovalWorkflow", null=True, blank=True,
                                 on_delete=models.SET_NULL,
                                 related_name="salary_raise_requests")
    current_step_order = models.PositiveSmallIntegerField(default=1)
    decisions = models.JSONField(default=list, blank=True)
    created_at = models.DateTimeField(auto_now_add=True)

# 2) ApprovalWorkflow.REQUEST_TYPE_CHOICES 加 ("salary_raise", _("加薪"))
# 3) 複製 punch_correction_views.py 的 submit / pending / decide 三個 view
# 4) urls.py 加 3 條 path；5) sidebar.py 加入口
# 6) 簽核關卡管理頁會自動出現這個新類型（讀 REQUEST_TYPE_CHOICES）

工期：2–3 天（含畫面）
