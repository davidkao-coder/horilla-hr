## 1. 架構全貌

### 1-1. 分層結構

```
┌─────────────────────────────────────────────────────────────┐
│ 表現層 Presentation                                          │
│  後台：Django Template（templates/ + 各 app templates/）      │
│  前台：單頁 App 風格（think4u/templates/think4u/portal/）      │
│  互動：HTMX（局部換 HTML）+ jQuery/select2 + 內嵌 vanilla JS   │
│  ⚠️ 無前端框架、無 npm build — 改 template 存檔即生效           │
└──────────────────────────┬──────────────────────────────────┘
                           │ HTTP / HTMX partial
┌──────────────────────────▼──────────────────────────────────┐
│ 視圖層 Views（函式型 view 為主，少量 Horilla CBV）             │
│  think4u/*_views.py（12 個模組）+ Horilla 原生 views          │
│  職責：權限判定 → 組 queryset → 呼叫規則層 → render/JsonResponse│
└──────────────────────────┬──────────────────────────────────┘
                           │
┌──────────────────────────▼──────────────────────────────────┐
│ 規則層 Business Rules（★ 本系統的核心設計）                    │
│  attendance_rules.py  出勤判定（pure functions, 無 DB 依賴）   │
│  payroll_rules.py     計薪公式（pure functions, 無 DB 依賴）   │
│  attendance_compute.py 出勤彙總（有 DB，組合上面兩者）          │
│  services/annual_leave_calculator.py 特休演算法（pure）        │
│  manager_utils.py     主管/部屬範圍判定                        │
└──────────────────────────┬──────────────────────────────────┘
                           │ Django ORM
┌──────────────────────────▼──────────────────────────────────┐
│ 資料層 Models                                                │
│  think4u/models.py（13 張自製表）+ Horilla 原生表              │
│  橫切：audit_log.py（signals 攔截全庫 CUD → AuditLog）         │
└──────────────────────────┬──────────────────────────────────┘
                           │
                    PostgreSQL 16
```

### 1-2. 為什麼「規則層」要獨立成 pure functions

`attendance_rules.py` 和 `payroll_rules.py` **完全不碰 DB、不 import Django model**，
輸入輸出都是原生型別（`time`、`int`、`dict`）。這是本系統最重要的架構決策：

| 好處 | 實際效益 |
|---|---|
| 可單獨測試 | 不用建資料就能驗算（特休 15 個案例測試靠這個）|
| 可重複使用 | 同一份計薪邏輯被「月度頁 / 即時 AJAX 儲存 / Excel 匯出」三處共用，**保證三處數字一致** |
| 規則變更好定位 | 勞健保級距調整只改常數，不動 view |

> **接手守則**：任何「算錢、算時數、算天數」的邏輯都寫進規則層，view 只負責取資料和呈現。
> 若在 view 裡寫計算，就會出現「頁面顯示與匯出 Excel 不一致」的經典 bug。

## 2. 技術選型與理由

| 決策 | 選擇 | 理由 | 代價 |
|---|---|---|---|
| 基底 | fork Horilla HRMS | 員工/部門/請假等基礎 model 與 CRUD 現成，省數月開發 | 綁死其架構、升級困難（見 docs/02）|
| 前端 | HTMX + Django Template | 團隊 1 人開發，無需前後端分離；SSR 首屏快 | 複雜互動（拖拉、即時協作）難做 |
| 部署 | Docker Compose | 環境一致、DB 版本可控 | 正式機需 rebuild image 才生效 |
| 客製隔離 | 獨立 `think4u/` app | 與上游程式分離，易識別自製範圍 | 少數原生檔仍需修改（見 docs/02 §3）|
| 計薪 | 自製而非用 Horilla payroll | 台灣勞健保級距/規則差異太大 | 自行維護級距表（每年更新）|
| 認證 | Django session + 自寫 OAuth | 不引入 allauth，減少依賴 | 自行維護 OAuth 流程 |

### 2-1. 為什麼不用 Horilla 原生的 Attendance
Horilla 的 `Attendance` / `AttendanceLateComeEarlyOut` 模型設計與台灣彈性工時規則不符，
且需搭配其 shift/work_type 體系。決策：**只寫 `AttendanceActivity`（打卡明細）**，
出勤狀態一律**即時計算**（`attendance_rules.evaluate()`），不落地儲存判定結果。

| 優點 | 規則調整後，歷史資料的判定自動跟著更新（不需回溯批次） |
|---|---|
| 缺點 | 每次看報表都要重算 → 月度頁需一次撈全月資料在記憶體算（見 §4 效能）|

## 3. 請求生命週期（含 Think4U 自製 middleware）

```
Request
  │
  ├─ ServerTimingMiddleware（自製）    → 量測並回寫 X-Server-Time 標頭
  ├─ SecurityMiddleware / WhiteNoise   → 安全標頭、靜態檔
  ├─ SessionMiddleware
  ├─ LocaleMiddleware                  → zh-Hant
  ├─ CsrfViewMiddleware
  ├─ AuthenticationMiddleware          → request.user
  ├─ MessageMiddleware
  ├─ XFrameOptionsMiddleware
  └─ AdminAccessGateMiddleware（自製） → ★ 前後台守門
        │
        ├─ force_admin_only 角色 + 訪問前台路徑 → redirect /
        └─ 無後台權限 + 訪問後台路徑          → redirect /portal/
              （白名單 ALLOWED_PREFIXES：/portal/ /clock/ /login /logout
                /landing /static/ /media/ /favicon.ico /reload-messages
                /forgot-password /reset-password）
  │
  ▼
View（權限二次判定：decorator 或 helper）
  │
  ▼
規則層計算 → Template render / JsonResponse
  │
  ▼（若有寫 DB）
Signals：audit_log post_save/post_delete → 寫 AuditLog
```

> ⚠️ **新增公開頁面（登入前可見）必須加進 `ALLOWED_PREFIXES`**，
> 且前綴**不要帶結尾斜線**（`/logout` 不是 `/logout/`），否則會被守門 middleware 導走。

## 4. 效能設計（已做的優化）

系統曾有明顯效能問題，經三輪優化，現況：一般頁面 warm < 100ms、47–72 queries。

| 問題 | 根因 | 解法 | 效果 |
|---|---|---|---|
| 每頁 60+ 多餘 SQL | `HorillaCompanyManager.get_queryset()` 每次跑兩條 COUNT 偵測重複 | 結果 cache 在 process-wide dict `_T4U_DISTINCT_CACHE` | query 降 40–65% |
| 部門/職位頁 N+1 | 逐筆再查員工數 | 改 `annotate(Count(distinct=True))` | 124→50 queries |
| 換頁載入慢 | 每頁載 ~29 個外部 JS，含 4.9MB 未使用的 pivottable | 刪除無用 JS，其餘移到專屬頁面 | 每頁少 4.9MB |
| 「第一下卡、第二下秒回」| gunicorn 預設 1 個 sync worker，背景輪詢佔滿 | 改 `gthread`，workers×threads = 2×4（正式 3×4）| 併發不再序列化 |
| 新增員工頁 cold 9.6s | view 內建了未使用的 form/filter | 移除無用物件 | 0.79s |

### 4-1. 月度統計頁的效能策略（最重的一頁）
`monthly_attendance_views.monthly_attendance()` 需算「N 員工 × 31 天」的矩陣，策略是：

1. **一次撈完**該月所有 `AttendanceActivity`、`LeaveRequest`、`Holidays`（3 次 query，非 N×31 次）
2. 在記憶體整理成 `by_emp_date` / `leave_minutes_by_emp_date` 字典
3. 迴圈內只做純計算（呼叫 `evaluate()`），**不再碰 DB**

> ⚠️ 改這頁時務必維持此模式。曾因在迴圈內計算請假分鐘導致 `AttributeError` 與效能退化。

## 5. 部署架構

### 5-1. 開發環境
```
Windows + Docker Desktop
  ├─ server 容器  8001→8000  gunicorn（整個專案目錄 bind mount，改檔即生效）
  └─ db 容器      5433→5432  PostgreSQL 16
```

### 5-2. 正式環境（Ubuntu 192.168.2.135）
```
Internet
   │ hrms.think4u-tech.com (DNS→106.104.136.29，路由器轉 80/443)
   ▼
系統 nginx（host，非容器；全公司共用 ★紅線資源）
   │  ├─ /media/ → alias /home/think4u/hrms/media/（直接服務）
   │  └─ /      → proxy_pass 127.0.0.1:8091
   ▼
docker compose -f docker-compose.deploy.yaml
   ├─ server  127.0.0.1:8091→8000（只綁 localhost）gunicorn 3×4
   ├─ db      PostgreSQL 16（volume 持久化）
   └─ backup  每日 pg_dump → ./backups（保留 30 天）
```

**與開發環境的關鍵差異**：
| 項目 | 開發 | 正式 |
|---|---|---|
| 程式來源 | bind mount（即時）| **烤進 image**（改程式要 `up -d --build`）|
| 靜態檔 | Django/WhiteNoise | WhiteNoise（collectstatic 於 build）|
| media | 容器內 | bind mount，由 nginx 直接服務 |
| DEBUG | True | False → **SECURE_SSL_REDIRECT 生效**（純 HTTP 會 301）|
| nginx | 無 | 系統 nginx（同機共用，改設定會影響其他站）|

> ⚠️ 正式機的 nginx 是**全公司共用**的反向代理，動它之前要確認不影響其他服務（TMS 也在同一台）。

## 6. 安全設計

| 層面 | 措施 |
|---|---|
| 認證 | Django session（密碼 PBKDF2）+ Google OAuth（僅公司網域、僅既有帳號、不自動開帳號）|
| 授權 | 兩層：middleware 守門（路徑層）+ view 內 helper/decorator（資料層）|
| 前後台隔離 | 無後台權限者**任何**後台路徑都被導走（白名單制，預設拒絕）|
| CSRF | Django 內建；正式站需設 `CSRF_TRUSTED_ORIGINS` |
| 傳輸 | 正式站 HTTPS（Let's Encrypt）+ `SECURE_SSL_REDIRECT` + HSTS 1 年 |
| 稽核 | 全庫 CUD 自動記錄（誰/何時/改了什麼欄位/舊→新值/IP）|
| 打卡防偽 | 每日 TOTP 驗證碼 + GPS 半徑判定 + 記錄 client IP |
| 密鑰管理 | 全部走 env（`.env` / `.env.prod`），不進版控；repo 內只有 `.example` 範本 |
| 檔案上傳 | 病假附件限副檔名（pdf/jpg/png）+ 10MB；nginx `client_max_body_size 20m` |

### 6-1. 已知安全缺口（接手須處理）
1. 全員密碼為同一組測試密碼（`docs/06` A1）
2. TOTP secret 在 `base/think4u_clock.py` 有 hardcode fallback——**正式環境必須用 env 覆蓋**
3. Google client secret 曾曝光，建議 rotate
4. 稽核紀錄無「唯讀保護」——具 DB 權限者可篡改

## 7. 可擴充性評估

| 情境 | 難度 | 說明 |
|---|---|---|
| 加一個新的簽核類型（如加薪申請）| 🟢 低 | 照 PunchCorrectionRequest 模式（狀態機 + decisions JSON），2–3 天 |
| 加薪資項目（如伙食津貼調整）| 🟢 低 | `SALARY_COMPONENT_FIELDS` 加欄位，UI 自動帶出 |
| 勞健保級距年度更新 | 🟢 低 | 改 `payroll_rules.py` 常數 |
| 把簽核關卡真正串進流程（Phase 4）| 🟡 中 | 需改請假/加班的核准 view，參考 punch_correction 的實作 |
| 多公司（multi-tenant）| 🔴 高 | Horilla 有 company_id 機制但系統已鎖單一公司，各處假設「只有一家」|
| 手機原生 App | 🔴 高 | 目前無 REST API 給前台用（horilla_api 存在但未用於 portal）|
| 換掉前端框架 | 🔴 高 | 所有頁面都是 Django Template + HTMX，等於重寫 |

## 8. 架構弱點與改善建議（給接手者的技術債清單）

| 弱點 | 影響 | 建議 |
|---|---|---|
| **計薪與出勤判定無自動化測試** | 改規則可能靜默算錯薪水 | 優先補 `payroll_rules` / `attendance_rules` 的單元測試（pure function，好寫）|
| 簽核邏輯有兩套（寫死 vs Workflow）| 認知負擔、行為不一致 | 完成 Phase 4，統一走 ApprovalWorkflow |
| 月度頁 view 過長（單一函式 ~200 行）| 難維護 | 抽出「矩陣組裝」與「薪資組裝」為獨立函式 |
| GPS 座標寫死在 py | 換辦公室要改程式 | 移到 DB 設定或 env |
| 無 CI/CD | 部署靠手動腳本 | 可加 GitLab CI（repo 已在 GitLab）|
| AuditLog 無分割/歸檔 | 表會持續長大（現 3.8 萬筆）| 已有 purge 指令，需設排程 |
