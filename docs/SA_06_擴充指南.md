# SA-06 擴充指南（Think4U HRMS）

> 「我要加一個新功能，該怎麼做？」——本文件給標準步驟 + 5 個實戰範例。

---

## 1. 標準開發流程（Checklist）

```
□ 1. 讀 docs/02 地雷清單，確認要動的區域有沒有雷
□ 2. Model 變更？
     → 寫在 think4u/models.py
     → makemigrations think4u && migrate
     → git add -f think4u/migrations/00XX_*.py  ★別忘 -f
□ 3. 業務邏輯 → 寫成 pure function 放規則層（attendance_rules / payroll_rules / services/）
     ★ 不要寫在 view 裡（會造成頁面與匯出不一致）
□ 4. View → think4u/<模組>_views.py
     → 權限：用 manager_utils.is_manager() / models.user_can_access_admin() 等 helper
     → 資料範圍：HR 全公司、主管 managed_employees()、員工自己
     → 排除隱藏員工：get_hidden_in_reports_employees()
□ 5. URL → think4u/urls.py（後台）或 portal_urls.py（前台）
     → 若是登入前可見的公開頁，加進 admin_gate_middleware.ALLOWED_PREFIXES
□ 6. Template → think4u/templates/think4u/<模組>/
     → 不改 Horilla 原生 template（要改就在 templates/think4u/ 覆寫）
     → 中文直接寫在 template 包 {% trans %}
□ 7. Python 內的使用者可見字串 → 用 gettext（英文 msgid）+ 補 po 翻譯
     → compilemessages -l zh_Hant（只編 zh_Hant！）
□ 8. Sidebar 入口 → think4u/sidebar.py（含 accessibility 函式）
□ 9. 測試 → think4u/tests/；規則層一定要有單元測試
□ 10. docker compose restart server（改 .py 才需要）
□ 11. 更新 CLAUDE.md Changelog + 相關 docs
□ 12. commit & push（origin=GitHub, gitlab=GitLab 兩邊都推）
```

## 2. 範例 A：新增一個「簽核類型」（如：加薪申請）

**最推薦的作法：照抄 `PunchCorrectionRequest`**（唯一完整走 ApprovalWorkflow 的模組）。

```python
# 1) think4u/models.py
class SalaryRaiseRequest(models.Model):
    STATUS_CHOICES = [("pending", _("待審核")), ("approved", _("已核准")),
                      ("rejected", _("已駁回"))]
    employee = models.ForeignKey(Employee, on_delete=models.CASCADE,
                                 related_name="salary_raise_requests")
    current_salary = models.PositiveIntegerField(verbose_name=_("現行薪資"))
    requested_salary = models.PositiveIntegerField(verbose_name=_("建議薪資"))
    reason = models.TextField(verbose_name=_("理由"))
    status = models.CharField(max_length=20, choices=STATUS_CHOICES, default="pending")
    # ★ 多關卡三本柱
    workflow = models.ForeignKey("think4u.ApprovalWorkflow", null=True, blank=True,
                                 on_delete=models.SET_NULL,
                                 related_name="salary_raise_requests")
    current_step_order = models.PositiveSmallIntegerField(default=1)
    decisions = models.JSONField(default=list, blank=True)
    created_at = models.DateTimeField(auto_now_add=True)
```

```python
# 2) ApprovalWorkflow.REQUEST_TYPE_CHOICES 加 ("salary_raise", _("加薪"))
# 3) think4u/salary_raise_views.py — 複製 punch_correction_views.py 的三個 view：
#    submit（員工提交，找 workflow、設 step 1）
#    pending（列出「我是這關簽核者」的申請）
#    decide（核准→step+1，最後一關→終態動作；駁回→rejected）
# 4) urls.py 加 3 條 path
# 5) sidebar.py 加入口（accessibility 用 manager_accessibility 或 hr_accessibility）
# 6) 簽核關卡管理頁會自動出現這個新類型（因為它讀 REQUEST_TYPE_CHOICES）
```
**工期估計**：2–3 天（含畫面）

## 5. 範例 D：調整出勤規則（如改成 09:00–09:30 彈性）

```python
# think4u/attendance_rules.py — 只改常數
CHECK_IN_FLEX_START = time(9, 0)
CHECK_IN_FLEX_END   = time(9, 30)
CHECK_OUT_FLEX_START = time(18, 0)
CHECK_OUT_FLEX_END   = time(18, 30)
```
**影響範圍**（全部自動跟著變，因為都呼叫 `evaluate()`）：
月度統計、當日明細、出勤異常紀錄、前台出勤頁、Excel 匯出、每日提醒。

⚠️ **注意**：出勤狀態是**即時計算**不落地，所以**歷史資料的判定也會跟著改變**。
若要「新規則只從某日生效」，需在 `evaluate()` 加日期參數分流（目前沒有這機制）。

**同步更新**：`docs/03 業務規則決策紀錄`、前台規則 banner 文字、`monthly.html` 說明文字。
**工期估計**：1 小時 + 測試

## 6. 範例 E：完成 Phase 4（讓請假吃 ApprovalWorkflow）★最大技術債

**目標**：把請假從寫死的「主管→HR」改為依 `ApprovalWorkflow` 設定跑多關卡。

**做法**：
```
1. LeaveRequest 是 Horilla 原生 model，不能加欄位（禁止改原生 migration）
   → 解法：新建 think4u.LeaveApprovalState（1:1 對 LeaveRequest）
     欄位：leave_request(OneToOne) / workflow / current_step_order / decisions(JSON)

2. 攔截請假建立：
   → portal_views.portal_leave_submit() 存 LeaveRequest 後，
     依員工職位找 ApprovalWorkflow(request_type='leave') 建立 LeaveApprovalState

3. 改寫簽核頁：
   → approval_views.manager_dashboard() 目前用 status='requested' 過濾
     改為：列出「LeaveApprovalState.current_step 的簽核者 == 我」的請假

4. 核准動作：
   → 每關核准 → current_step_order += 1
   → 最後一關 → LeaveRequest.status = 'approved' + 扣 AvailableLeave

5. 相容處理：
   → 沒有 workflow 設定的職位 → fallback 走原本「主管→HR」
     （避免既有資料/未設定職位卡住）

6. 參考實作：punch_correction_views.py 的 decide() 是完整範本
```
**工期估計**：5–8 天（含測試與資料遷移）
**風險**：請假是最常用的功能，改壞影響最大 → 建議先寫測試、分階段上線。

## 7. 常見陷阱與慣例

| 陷阱 | 正確做法 |
|---|---|
| 想改 `attendance/views.py` | 改 `attendance/views/views.py`（同名 module 被 package 蓋掉）|
| 想讀出勤狀態 | 用 `attendance_compute.daily_evaluations()`，別讀原生 `Attendance` 表（空的）|
| 用 `is_reportingmanager` 判主管 | 用 `manager_utils.is_manager()`（含部門主管）|
| 在 view 裡算薪水 | 呼叫 `payroll_rules` 的 pure function |
| 新增 migration 後直接 commit | 要 `git add -f`（`**/migrations/**` 被 gitignore）|
| Python 裡寫中文字串 | 用 `gettext` + po 檔 |
| `compilemessages` 全語系 | 只編 `-l zh_Hant`（其他語系 po 有格式 bug）|
| 新公開頁面 500/被導走 | 加進 `ALLOWED_PREFIXES`（前綴不帶結尾斜線）|
| 批次建 Horilla model 拋 TypeError | 先 `Model.save = dj_models.Model.save` |
| git-bash 執行 `docker compose exec` 帶路徑 | `export MSYS_NO_PATHCONV=1` |
| 正式機改程式沒生效 | 要 `up -d --build`（image 內含程式，非掛載）|

## 8. 建議的優先開發順序（給接手者）

| 優先 | 任務 | 理由 |
|---|---|---|
| 🔴 1 | 補 `payroll_rules` / `attendance_rules` 單元測試 | 目前無測試保護，改規則等於盲改；pure function 好寫 |
| 🔴 2 | 完成正式部署收尾（nginx/憑證/資料還原）| 系統還沒真正上線 |
| 🔴 3 | 安全項：改全員密碼、設 SMTP、rotate Google secret | 見 docs/06 A |
| 🟠 4 | Phase 4（請假吃 ApprovalWorkflow）| 最大功能落差 |
| 🟠 5 | 排程建立（未打卡提醒、稽核清理、異地備份）| 維運基礎 |
| 🟡 6 | 產假半薪、補休自動轉換、離職當月比例 | 法規/功能完備性 |
| 🟡 7 | 月度頁 view 重構（拆函式）、GPS 座標移到設定 | 可維護性 |

## 9. 開發環境速查

```bash
# 起環境
docker compose up -d && docker compose logs -f server

# 改 .py 後
docker compose restart server

# 改 po 後
export MSYS_NO_PATHCONV=1
docker compose exec -T server python manage.py compilemessages -l zh_Hant
docker compose restart server

# Model 變更
docker compose exec -T server python manage.py makemigrations think4u
docker compose exec -T server python manage.py migrate
git add -f think4u/migrations/00XX_*.py

# 測試
docker compose exec -T server python manage.py test think4u.tests

# 進 shell 驗算
docker compose exec -T server python manage.py shell

# 部署（日常）
bash scripts/deploy_to_server.sh
```
